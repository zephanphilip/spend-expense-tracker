Mobile-first personal expense tracker. Next.js (App Router) + Firebase (Auth + Firestore),
rendered entirely on the client for authenticated screens; Firestore Security Rules are the
authorization boundary.

## Domain types (src/types/index.ts)

```ts
type PaymentMethod = "credit" | "debit" | "upi" | "cash";
type CurrencyCode  = "INR" | "USD" | "EUR" | "GBP" | ...;

interface UserProfile { uid; email; displayName; photoURL; currency; createdAt; updatedAt }
interface Category    { id; name; icon: CategoryIconKey; color: CategoryColorKey;
                        isDefault: boolean; archived: boolean; createdAt?: Date }
interface Expense     { id; amount /* integer minor units */; categoryId; paymentMethod;
                        note; occurredAt: Date; createdAt: Date; updatedAt: Date }
type ExpenseInput = Pick<Expense, "amount"|"categoryId"|"paymentMethod"|"note"|"occurredAt">;
interface ExpenseQuery { from?: Date; to?: Date; categoryId?: string;
                         paymentMethod?: PaymentMethod; limit: number }
```

Money is stored as an **integer number of minor units** (paise/cents) to avoid float drift.

## Firestore collections

```
users/{uid}                          UserProfile
users/{uid}/expenses/{expenseId}     amount:int, categoryId:string, paymentMethod:string,
                                     note:string, occurredAt:timestamp,
                                     createdAt:timestamp, updatedAt:timestamp
users/{uid}/categories/{categoryId}  name, icon, color, archived:bool,
                                     createdAt, updatedAt          (custom only)
```

* **Default categories live in code** (`lib/constants/categories.ts`) with stable slug IDs
  (`food`, `transport`, …) and are merged with the user's custom categories at read time.
  No seeding writes at sign-up, no race on first login, and defaults can improve with app
  releases. Custom category IDs are Firestore auto-IDs, so they never collide with slugs.
* Custom categories are **archived** rather than deleted so historical expenses still render
  their name/icon.
* Everything is nested under `users/{uid}` so ownership is structural and rules are simple.

## Indexes (firestore.indexes.json)

| Collection | Fields | Used by |
|---|---|---|
| expenses | occurredAt DESC (single-field, automatic) | dashboard, history |
| expenses | categoryId ASC, occurredAt DESC | history filtered by category |
| expenses | paymentMethod ASC, occurredAt DESC | history filtered by payment method |
| expenses | categoryId ASC, paymentMethod ASC, occurredAt DESC | both filters |

`note` is exempted from single-field indexing (never queried; saves write cost).
Free-text search runs client-side over the loaded window.

## Security rules (firestore.rules)

* Default deny for everything.
* `users/{uid}` and all subcollections: only `request.auth.uid == uid`.
* Strict schema validation on every write: allowed keys only, types, enum for
  `paymentMethod`, `amount` positive integer ≤ 10^12, `note` ≤ 280 chars, category name
  1–32 chars, icon/color from allow-lists.
* `createdAt == request.time` on create, immutable afterwards; `updatedAt == request.time`
  on every write (service uses `serverTimestamp()`).
* Profile cannot be deleted from the client.

## Component architecture

```
RootLayout
 └─ ThemeProvider → AuthProvider → Toaster, ServiceWorkerRegistrar
     ├─ (auth) GuestGuard → AuthShell → AuthForm / GoogleButton
     └─ (app)  AuthGuard → CategoriesProvider → ExpenseSheetProvider → AppShell
                 ├─ Sidebar (md+) / BottomNav (mobile) / AddExpenseFab
                 ├─ page content (Dashboard, Expenses, Categories, Settings)
                 └─ ExpenseSheet (ResponsiveModal: vaul Drawer on mobile, Dialog on desktop)
                      └─ ExpenseForm (RHF + Zod)
                           AmountInput · CategoryPicker · PaymentMethodPicker ·
                           note Input · DateTimeField · DeleteExpenseDialog (edit mode)
```

* UI never imports `firebase/*`; it calls `lib/services/*` and hooks built on them.
* Live data via `onSnapshot`, with Firestore's persistent local cache so the app opens
  instantly and works offline; writes resolve optimistically if the network is slow.
* `ExpenseSheetProvider` exposes `openCreate()` / `openEdit(expense)` so any screen (FAB,
  list row, dashboard) can open the same sheet.

## Auth & route protection

Firebase Auth runs on the client, so route protection is a client guard (`AuthGuard`)
that renders a skeleton until auth state is known and redirects to `/login?next=…`.
Data protection does not depend on it: every read/write is enforced by Security Rules.
(Server-side session cookies would need Firebase Admin; deferred.)

# Phase 2 — personal financial management

## Navigation

Still four tabs and the Add button: **Home · History · [+] · Plan · Settings**. *Plan* replaces
the old Categories tab and is a hub linking to Monthly summary, Budgets, Income & salary, EMIs,
Wishlist and Categories (each sub-page has a back link; the desktop sidebar lists them inline).
Creation and edits happen in bottom sheets (dialogs on desktop), never extra pages.

## New Firestore data (all under `users/{uid}`)

| Path | Shape | Notes |
|---|---|---|
| `budgets/{yyyy-MM}` | `month, overall: int\|null, categories: {categoryId: int}, updatedAt` | One doc per month. A month without its own doc **inherits** the latest earlier one, so budgets roll forward until changed. History = effective budget vs spend per month. |
| `incomes/{id}` | `amount, source (salary\|freelance\|bonus\|other), note, receivedAt, forMonth: yyyy-MM, expectedAt\|null, recurringId\|null, createdAt, updatedAt` | `forMonth` attributes income to a month (September salary paid 1 October counts for September). Salary records are incomes with `source = salary` + `expectedAt`. |
| `recurringIncomes/{id}` | `name, source, amount, dayOfMonth, startMonth, active, createdAt, updatedAt` | Templates. Each month an un-recorded template appears as *expected*; "Received" creates `incomes/{templateId}_{month}` in a **transaction**, so it can't be recorded twice. |
| `emis/{id}` | `name, lender, principal, annualRateBps, monthlyAmount, tenureMonths, startDate, paidCount, outstanding, status, createdAt, updatedAt` | Reducing-balance amortisation. `alreadyPaid` on create supports loans started before the app. |
| `emis/{id}/payments/{installment}` | `installment, amount, principalPart, interestPart, dueDate, paidAt, expenseId\|null, createdAt` | Doc id = installment number. |
| `goals/{id}` | `name, icon, color, targetAmount, savedAmount, targetDate\|null, status, lastOpId, createdAt, updatedAt` | Wishlist items. |
| `goals/{id}/contributions/{id}` | `amount (± for withdrawals), note, contributedAt, createdAt` | |

Money is still integer minor units everywhere; interest rate is basis points (10.5% → 1050).

## Consistency (transactions + rules)

* **EMI payment** — one transaction re-reads the loan, writes `payments/{n}`, decrements
  `outstanding` by the principal part, bumps `paidCount`, closes the loan on the last
  installment, and (optionally) creates the matching expense in the built-in **EMI** category.
  *Undo* reverses all of it (including the expense) in one transaction.
* **Goal contribution / withdrawal** — one transaction writes the contribution and the new
  `savedAmount`; withdrawals can't take the balance below zero.
* **Recurring income** — transaction on the deterministic id prevents duplicates.
* **Rules cross-check the writes** (`get()`/`getAfter()`/`existsAfter()`):
  a payment must be installment `paidCount + 1` and land in the same write as the loan update;
  `paidCount` can only move ±1 together with creating/deleting that payment; only the latest
  payment can be deleted; a goal's `savedAmount` can only change when `lastOpId` names a
  contribution created or deleted in the same write, and the contribution's amount must equal the
  balance delta; recurring incomes must use the `{templateId}_{month}` id.
* Deleting a loan/goal removes the parent first, then children in ≤450-write batches
  (rules allow orphan cleanup only once the parent is gone).

## Indexes

Added `incomes (source ASC, receivedAt DESC)` for salary history; `note` fields on incomes and
contributions are exempt from indexing. Month-range income queries use `forMonth` only
(single-field). Budgets order by `month`, payments by `installment`, contributions by
`contributedAt` — all single-field.

## Monthly summary maths

`savings = income (by forMonth) − expenses (by occurredAt)`, `savingsRate = savings / income`
(undefined without income). EMI obligations for a month are derived from each loan's schedule
(installment due that month, paid if `≤ paidCount`) — no extra query. EMI payments logged as
expenses already count in `expenses`; the EMI section is informational. Budget utilisation uses
the month's effective overall budget.

# Phase 3 — accounts, transfers, cards, investments, recurring payments, net worth

## Transaction architecture

Every balance-affecting record carries an explicit type:

| Type | Stored in | Balance effect | Counts as spending? |
|---|---|---|---|
| `EXPENSE` | `expenses` | account −amount (card: debt +amount) | **yes** |
| `INCOME` | `incomes` | account +amount | — |
| `TRANSFER` | `transfers` | from −amount, to +amount | no |
| `DEBT_PAYMENT` | `transfers` (to a card, or `emiId` for loans) | from −amount, card +amount (debt ↓) | no |
| `INVESTMENT` | `investmentTransactions` (BUY / SELL / VALUATION) | BUY −amount, SELL +amount, VALUATION none | no |

* `lib/finance/ledger.ts` is the single definition of these effects (create, edit = undo old +
  apply new, delete = reverse). Services apply them as `FieldValue.increment()` in the **same
  batch/transaction** as the record, so balances can't drift and offline entry still works.
* Spending analytics (dashboard, budgets, summary) only read `expenses`, so transfers and
  card payments can't be double-counted: card spend is counted once when it happens; paying
  the card later just moves money from bank to card.
* EMI installments paid from an account create a `DEBT_PAYMENT` (`emi_{emiId}_{n}`) that
  debits the account once. The optional "count in spending" expense is *not* linked to the
  account, so the money leaves the account exactly once either way.
* Each transfer is one document with both sides (`fromAccountId` / `toAccountId`) — the two
  legs are inseparable. Account activity merges expenses, incomes, both transfer directions
  and investment cash flows into one ledger with a running balance (`lib/finance/activity.ts`).

## Migration

Additive only — no data was moved. Phase 1/2 expense and income documents without `type` /
`accountId` read as `EXPENSE`/`INCOME` with no account (converter defaults), and the rules
accept both shapes. New writes always include the fields. Users without accounts see no change.

## New collections (under `users/{uid}`)

| Path | Key fields |
|---|---|
| `accounts/{id}` | `name, type (bank\|cash\|wallet\|credit_card), institution, openingBalance, balance, active, creditLimit, statementDay, dueDay, statementBalance, minimumDue, lastOpId` |
| `transfers/{id}` | `type (TRANSFER\|DEBT_PAYMENT), amount, fromAccountId, toAccountId\|null, emiId\|null, emiInstallment\|null, note, occurredAt` |
| `investments/{id}` | `name, kind (mutual_fund\|stock\|fd\|gold\|crypto\|other), investedAmount, currentValue, realizedGain, purchaseDate, lastValuedAt, status, lastOpId` |
| `investmentTransactions/{id}` | `investmentId, type: INVESTMENT, kind (BUY\|SELL\|VALUATION), amount, costBasis, accountId, note, occurredAt` |
| `recurringPayments/{id}` | `name, amount, categoryId, paymentMethod, accountId, unit (day\|week\|month\|year), interval, startDate, cycle, nextDate, endDate, active` |
| `netWorth/{yyyy-MM}` | `assets, liabilities, netWorth` (monthly snapshot) |

`expenses`, `incomes`, `recurringIncomes` and EMI `payments` gained an optional `accountId`.

**Sign convention:** balances are signed minor units. A credit card's balance is negative
while you owe (`outstanding = −balance`), which makes spending, transfers and card payments the
same arithmetic.

## Calculations (all pure + unit-tested)

* **Cards** — utilisation = outstanding / limit; available = limit − outstanding; billing cycle
  from statement/due days (due falls next month when `dueDay ≤ statementDay`); suggested
  minimum due 5% (min ₹200, never above the statement). Payments reduce statement and minimum due.
* **Investments** — returns = current − invested; selling removes cost basis proportionally
  (`invested × sold / currentValue`, all of it on full exit) and books `realizedGain`.
* **Recurrence** — occurrence *n* = start + n×interval units, computed from the start date so
  month-end schedules don't drift; paying writes `expenses/rp_{id}_{cycle}` (can't pay twice).
* **Net worth** — assets: bank + cash + wallet balances + active investment value (+ any card
  credit); liabilities: card outstanding + active EMI outstanding.
* **Upcoming** — recurring occurrences, next EMI due, card bills (from statement), expected
  recurring income; overdue items included; next 30 days.

## Security rules

* `moved(id, delta)`: an account exists before/after and its balance changed by exactly
  `delta` in this request. Expenses, incomes, transfers and investment transactions must apply
  their exact effect on create, edit (difference, or refund + debit when switching accounts)
  and delete (`movedOrGone` tolerates deleted accounts in old history).
* Accounts: `balance == openingBalance` on create; the ledger-derived part (balance − opening)
  may only change when `lastOpId` gets a fresh per-write stamp; type is immutable; card fields
  only on cards. Reconciliation shifts opening and balance together.
* Transfers: different accounts; `TRANSFER` can't target a card; `DEBT_PAYMENT` must target a
  card or be an EMI payment with id `emi_{emiId}_{n}` written together with that installment;
  only note/date are editable.
* Investments: amounts change only with a new history entry named by `lastOpId`; BUY/SELL/
  VALUATION each verify the holding's invested/current deltas and the account movement.
* Recurring payments advance one cycle at a time (or restart at 0 after rescheduling).
* Net-worth snapshots must satisfy `netWorth == assets − liabilities`.

## Indexes added

`expenses (accountId, occurredAt↓)`, `incomes (accountId, receivedAt↓)`,
`transfers (fromAccountId, occurredAt↓)`, `transfers (toAccountId, occurredAt↓)`,
`investmentTransactions (investmentId, occurredAt↓)`, `investmentTransactions (accountId, occurredAt↓)`;
`note` exempted on transfers and investment transactions.

## Navigation

Still four tabs. The Plan hub is grouped: **This month** (Summary, Budgets, Upcoming) ·
**Money** (Accounts & cards, Investments, Net worth) · **Plans** (Income, Recurring payments,
EMIs, Wishlist) · **Setup** (Categories). The dashboard adds a net-worth tile and a
"Coming up" list (next 14 days) with one-tap Pay / Received actions.

# Phase 4 — analytics, insights and CSV import/export

## Derived monthly aggregates (`users/{uid}/monthlyStats/{yyyy-MM}`)

`expenseTotal, expenseCount, incomeTotal, incomeCount, byCategory, byPaymentMethod, byAccount,
byDay ("01"…"31"), incomeBySource, version`.

* **Maintained in the same batch/transaction** as every expense/income write (create, edit,
  delete, undo, EMI-logged expense, recurring payment, recurring income, CSV import/undo) via
  `set(..., {merge: true})` + `increment()` — offline-safe, no extra reads.
* **Only `EXPENSE` and `INCOME` feed them**, so transfers, card payments and investment cash
  flows can never inflate spending — consistent with the Phase 3 transaction architecture.
  Income is attributed by `forMonth`.
* **Self-healing:** a month whose document is missing or lacks the current `version` (e.g.
  data from before Phase 4) is rebuilt from source with two bounded queries, once. A
  randomised test (300 creates/edits/deletes) proves increments equal a full rebuild.

## Query strategy (no full-history downloads)

| View | Source |
|---|---|
| Whole-month periods, no filters | aggregates only (≤ ~24 small docs for trends + comparison) |
| Filters (category/account/method), custom or partial ranges | raw expenses **for that span only** (cap 5,000, flagged if hit) |
| In-progress comparison (e.g. 1–7 Oct vs 1–7 Sep) | aggregates for the current month, raw for the partial previous slice |
| 12-month income vs expenses, category trends, savings rate | aggregates |
| CSV duplicate check | existing records in the file's date span only |
| CSV export | everything (explicit user action) |

`spendFromStats` and `spendFromExpenses` return the same `SpendData` shape; a test asserts they
are identical for whole months.

## Analytics (`lib/analytics/*`, pure + tested)

Periods (this/last month, 3/6/12 months, this year, custom) with like-for-like previous
periods; totals and change; category, payment-method and account breakdowns (top N + "Other");
daily, weekly (Mon-start) and monthly series; weekday averages; calendar heatmap (rank-based
4-level single-hue ramp); category trends; income vs expenses, savings and savings rate;
budget utilisation and over-budget categories; card utilisation; EMI and recurring burden vs
average income; annualised subscriptions; investment overview; net-worth trend; wishlist.

**Insights** (`insights.ts`) are deterministic rules with explicit thresholds
(`THRESHOLDS`): spending change ≥ 15% and ≥ ₹1,000; category ≥ 1.5× its 3-month average;
over-budget categories; recurring ≥ 25% / EMI ≥ 40% of income; savings-rate shift ≥ 5 points;
card utilisation ≥ 30% (≥ 75% high); largest category; weekday ≥ 1.4× daily average. Each
insight's text states the numbers and the rule that triggered it.

## Charts

Recharts, following the data-viz rules: validated categorical slots (payment methods, accounts
and investment kinds have fixed slots; categories keep their own colours — colour follows the
entity), one y-axis per chart, thin bars with 4 px rounded ends, hairline solid grid, 2 px
surface gaps in stacks, hover tooltips, a legend for ≥ 2 series, a "View as table" toggle on
every chart, dark-mode steps defined separately (`--series-*`, `--heat-*` tokens).

## CSV

* `lib/csv/csv.ts` — RFC 4180 parser (quotes, embedded delimiters/newlines, CRLF, BOM;
  auto-detects `,` `;` tab) and writer (BOM for Excel, CSV-injection guard for `= + - @`).
* **Export** (`/data`): expenses, income, budgets, EMIs, accounts & cards, investments,
  recurring payments, wishlist, categories — plain-number amounts, ISO-like dates.
* **Import** (expenses or income): file checks (≤ 2 MB, ≤ 5,000 rows, header) → column
  auto-mapping + date-format detection (editable) → preview with per-row status and reasons
  (invalid / duplicate in file / already saved; fingerprint = day + amount + note) → explicit
  confirmation (duplicates skipped unless opted in) → batched writes of **new documents only**
  (chunks of 200, aggregates updated in the same batches) → summary (imported / skipped /
  duplicate / invalid). Every row carries `importId`; an `imports/{id}` log enables **Undo
  import**. Imported rows aren't linked to accounts (current balances already include them).

## Rules & indexes

`monthlyStats` (owner-only, shape-checked derived cache), `imports` (status-only updates, no
delete); expenses/incomes accept an optional `importId`. Month-range stats queries and
`importId` lookups use single-field indexes — no new composite indexes.

# Phase 5 — production hardening

## PWA & iPhone
* Manifest: standalone, portrait, maskable icons, **shortcuts** (Add expense → `/dashboard?add=expense`,
  History, Analytics). iOS **launch screens** for 10 iPhone sizes × light/dark (`npm run splash`).
* Service worker (production only): network-first navigations with an **offline app shell**
  (core screens pre-cached), cache-first hashed assets, notification click → in-app navigation
  (same-origin only). Firestore's persistent cache supplies data offline; writes queue and sync.
* `NetworkStatus`: offline banner driven by `navigator.onLine` **and** an uncached connectivity
  probe (handles captive portals / emulated offline), "Back online" toast on recovery.
* Safe areas on every fixed surface; thumb-zone tab bar; large decimal keypad amount input;
  `prefers-reduced-motion` respected; vibration "haptics" on Android (iOS: visual feedback).
* Double-submission guard on Add Expense (ref guard on top of the disabled button).

## Quick actions
`N` add expense · `/` search · `G` then `H/E/P/A/S` navigate · `?` help (ignored while typing
or in dialogs). PWA shortcuts and the `?add=expense` deep link open the Add sheet directly.

## Theme
Light / dark / system via next-themes (persisted per device), dark-mode chart tokens and
splash screens, `theme-color` per scheme.

## Backup & restore (`lib/backup/format.ts`, `services/backup.service.ts`)
* Versioned JSON (`app: "ledger", version: 1`) of every collection incl. sub-collections
  (EMI payments, goal contributions); timestamps encoded as `{"$date": ISO}`. Server-managed
  fields (`createdAt`, `updatedAt`, `lastOpId`, `importId`, `restoreId`) are stripped.
  `monthlyStats` is derived and rebuilt after restore.
* **Validation**: header/version check, per-collection Zod schemas mirroring the security
  rules with `.strict()` (unknown fields rejected), id format, sub-collection parents, budget
  id = month; invalid documents are listed and skipped.
* **Preview & duplicates**: counts per collection of new / already-present (same id) /
  duplicate (same date + amount + note for expenses & income). **Nothing is ever overwritten.**
* **Restore**: opens a `restores/{id}` session; documents carry `restoreId` and are written in
  dependency order (accounts before transfers, loans before payments…) in 400-doc batches.
  Rules relax ledger cross-checks *only* for documents stamped with an open session that is
  < 1 hour old; sessions can only be closed, never reopened. Transfers referencing missing
  accounts are reported as orphaned. Monthly aggregates for touched months are rebuilt.

## Recurring automation (`lib/finance/automation.ts`, `hooks/use-recurring-automation.ts`)
* "Record automatically" on recurring payments (`autoPay`) and recurring income (`autoRecord`).
* On app open / foreground (≥ 5 min apart, online only) a pure planner lists due occurrences
  (capped at 24 per run); each is executed by a transaction that re-reads the schedule and
  requires the expected cycle, writing `expenses/rp_{id}_{cycle}` (or
  `incomes/{template}_{month}`) — **idempotent across re-runs, reloads and devices**.
* Generated expenses keep **occurrence references** (`recurringId`, `occurrence`) and are
  dated on the occurrence's due date; the list shows a recurring marker.

## Reminders (`lib/finance/reminders.ts`)
EMI due, card bills, recurring payments within a lead time (0–7 days) and budget warnings
(≥ 80% / over, from this month's aggregate). In-app reminder centre (bell) always; device
notifications via the service worker when the app opens — at most once per reminder per day.
Preferences are per device. *Push while the app is closed would need FCM + Cloud Functions
(a server); deliberately not faked.*

## Security
* **Firestore rules**: owner-only everywhere, default deny, strict schemas, ledger/balance
  invariants (Phase 3), restore sessions (above). 72 emulator tests.
* **App Check** (reCAPTCHA v3) when `NEXT_PUBLIC_FIREBASE_APPCHECK_SITE_KEY` is set; debug
  tokens for CI. Enforce per product in the console after monitoring.
* **Headers**: CSP (prod), HSTS (prod), `X-Frame-Options: DENY`, `nosniff`,
  `Referrer-Policy`, `Permissions-Policy`, COOP `same-origin-allow-popups` (Google sign-in),
  no `X-Powered-By`. E2E runs against the production build to prove CSP compatibility.
* **XSS**: React escaping only — no `dangerouslySetInnerHTML`/`eval` anywhere. **CSV
  injection** neutralised on export. Strict Zod validation in every service before writes;
  open-redirect-safe `?next=`; notification URLs restricted to same origin.
* **Environment**: `.env.example`, `.env.staging.example`, `.env.production.example`;
  `prebuild` fails on missing config or production+emulators. Separate Firebase projects per
  environment (`.firebaserc` aliases, `deploy:rules:staging|production`).

## Performance
* Monthly aggregates now back Summary, Budgets, the Plan hub and Analytics (≤ 24 small docs
  instead of months of transactions); raw reads only for filtered/custom analytics and lists.
* Paginated history (load older), capped activity/history queries, persistent offline cache.
* Route-level code splitting: Recharts (~125 KB gz) only on `/analytics`; CSV/backup only on
  `/data`; Performance Monitoring SDK lazy-loaded. `optimizePackageImports` for lucide,
  recharts, date-fns. Memoised expense rows and day grouping.

## Errors & monitoring
Route error boundary with retry, global error page, not-found page; Firebase Performance
Monitoring (opt-in via env) for page-load and network traces.
